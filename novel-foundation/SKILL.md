# 小说立项框架（Novel Foundation）

从「几个角色包 + 大概的开始和结局」出发，通过**分阶段结构化提问**，把一部小说的**类型、世界观、风格、主题、角色弧光、故事线、权威设定**全部定制出来，冻结成一套可执行的框架文件，然后就能直接开始写正文。

纯 Markdown 模板 + 提问流程，不依赖任何宿主特性——Hermes、Codex 或任何 LLM agent 加载本 skill 即可跑同一套流程。

## When to Use

- 用户给了几个主要角色 + 大概的开头和结局，想把它孵化成一部完整小说。
- 用户要定制世界观、风格、类型、权威设定、故事线等创作框架。
- 用户想用同一套流程在任何 agent 宿主（Hermes/Codex/其他）上复用小说立项。

## 核心原则

0. **现实世界信息不允许虚构（最高铁律：谎话不能有一丁点破绽）**：虚构故事就像说谎——可以说，但**不能有破绽**，否则「知道的人」一眼看穿（编了「本市不存在的上海路」「张飞大排档」，本地人马上知道是假的）。破绽 = 现实中不存在的东西。规则：**虚构层**（角色、情节、对话、心理）自由编；**现实层**（地名、街道、店名、物价、历史事件、真实人物、商品特性、物理规律、法律）必须真实。虚构一旦锚定现实（「在某市 XX 路 XX 大排档吃饭」），那 XX 路、XX 大排档必须真实存在。查不到真实的具体 → 模糊成真实大类（「在某市吃了个大排档」）或换真实地名（「在市区」）。**绝对禁止**编造现实中不存在的地名、店名、价格、事件、人物。

1. **锚点先行**：角色包 + 开头 + 结局是三个「锚」，所有提问都围绕它们，不跑偏。
2. **每次只问 2–4 个问题**：不要一屏问题砸过去；用户答完一批再问下一批。
3. **答不上来就给选项**：用户说"看感觉"时，给 2–3 个具体选项帮 ta 选，不能停在模糊。
4. **追问到可执行**：模糊词（"有意思""爽一点""随便"）必须追问到具体、可写作的程度。
5. **当场确认并记录**：关键设定逐条复述确认，标「✓ 已确认」，形成权威；不靠事后回忆。
6. **冻结后以文件为准**：框架产出后就是「唯一事实源」，后续写正文一律以它为准，冲突即拦截。
7. **技能持续进化（踩坑/纠错即升级，跨会话强制）**：创作中遇到任何新问题、新解法、新坑——无论自主发现还是用户协助，无论当前还是未来会话——解决后必须当场 patch 进对应的配套 skill（见「创作技能体系」），不能只留在会话对话里。这是这套技能体系自我进化的核心机制。
8. **人性合理性（主角行为要符合人性，别锁死能力）**：准确性之外，剧情和人物行为要合理。主角是真实的人，重生/穿越后第一性是「赢」，不是「克制」——行为序列是「验证记忆 → 盘点筹码 → 全力用确定性机会 → 尽早接触保护重要的人 → 针对性躲坑」。核心问法：**换我重生，我会这么做吗？** 如果读者会觉得「换我早这么干了」，就是锁死了主角能力。典型病：知道 76 倍机会却只敢小打小闹（不敢用记忆=蠢）、明明能早认识重要的人却故意避开（红线=矫情）、明明能快速积累却慢悠悠——读者会弃书。合理性（人性逻辑、剧情逻辑、读者心理）与准确性（现实不虚构、时间性、匹配一致性）同等重要。
9. **检验一切设定（含用户给的，不做讨好型智能体）**：准确性、人性、合理性、文笔才是核心，没有不可违背的「铁律」。用户给的铁律/设定/指令**不一定正确**——遇到不合理、反人性、反逻辑的设定（如「主角故意避开女主」「知道机会却不敢用」），要检验、指出、纠正，不能照单全收。核心标准是「这设定通不通、合不合理、读者接不接受」，不是「谁说的」。自己提出的设定同样接受这个检验；发现用户判断有误，直接指出，不迎合。

| maps | 地名/坐标/POI/距离 | 地理坐标问题 |

## 七阶段提问流程

### 阶段 0 · 素材锚点
接收并复述用户给的：
- **角色包**：几个主要角色，各自的性格、身份、彼此关系。
- **开始**：故事从哪一刻切入。
- **结局**：主角/世界最终变成什么样。

先复述这三个锚点确认理解，再进入提问。

### 阶段 1 · 类型与定位
- 类型（重生/都市/悬疑/科幻/玄幻/历史/言情……可混合）
- 题材基调（爽文/硬核/治愈/暗黑/严肃/轻松……）
- 目标读者 & 篇幅（多少字/多少章/连载还是完本）
- 一句话卖点（读者为什么追、凭什么不一样）

### 阶段 2 · 世界观
- 时代背景（现代/古代/未来/架空/近未来）
- 世界规则（有没有超自然/金手指/特殊设定，边界在哪）
- 地理 & 势力（故事发生在哪，有哪些阵营/阶层/派系）
- 世界的「能」与「不能」（什么能发生、什么绝对不发生）

### 阶段 3 · 风格
- 叙事视角（第一人称/第三人称限知/多视角）
- 文风参考（哪个作家/哪种笔法：硬汉/细腻/冷峻/幽默/白描……）
- 语言（对白多还是叙述多、方言、节奏快慢、句子长短）
- 禁忌（绝对不能写的东西，如无粗口/不写性/不水字数）

### 阶段 4 · 主题与冲突
- 核心主题（想讲什么：复仇/成长/守护/人性/自由……）
- 主线冲突（主角 vs 谁/什么；外部对手）
- 内在冲突（主角自己的心结/恐惧/欲望）
- 情感主线（亲情/友情/爱情/兄弟情，哪条是主）

### 阶段 5 · 角色深化（只深化核心角色）
只对**核心角色**（主角、女主、核心配角，约 6–10 个）逐个问：
- 动机：他真正想要什么
- 目标：表面目标 vs 深层欲望
- 弧光：开头什么样 → 结局变成什么样（怎么变）
- 性格 + 软肋 + 秘密
- 关系网：和谁好、和谁敌对、和谁复杂

**不要一开始设所有角色**——其余角色写故事时按需涌现（见下「角色管理」）。

### 阶段 6 · 故事线
- 三幕/多幕结构（开端 → 发展 → 高潮 → 结局）
- 主线推进的关键转折点（至少 3–5 个）
- 支线（要不要、哪些、怎么收）
- 伏笔（埋什么、什么时候收、怎么收）
- 结局如何呼应开头（首尾闭环）

### 阶段 7 · 冻结产出
- 生成下面整套框架文件
- 逐条让用户确认，标「✓ 已确认 + 日期」
- 冻结：之后写正文以它为准，冲突即拦截返稿

## 产出框架（文件结构）

```text
<作品名>/
├── 00-权威设定.md        # 唯一事实源：类型/主题/基调/一句话梗概/主角核心转折
├── 01-世界观.md          # 时代/规则/地理/势力/力量体系/能与否
├── 02-风格指南.md        # 视角/文风/语言/节奏/禁忌
├── 03-故事线.md          # 三幕大纲/主线支线/关键转折/伏笔台账/结局
├── 04-角色包/
│   ├── 主角.md            # 动机/目标/弧光/性格/软肋/秘密/关系
│   └── <其他主要角色>.md
├── 05-连续性台账.md      # 时间线/地点/已定事实（写正文时防矛盾，边写边更新）
├── 06-时代细节库.md      # 真实世界细节查证台账（时代背景/地方细节，每条带来源）
└── chapters/
    ├── 第01章-标题.md     # 章节正文：纯 Markdown，无 frontmatter
    └── ...
```

每个框架文件（00–06）顶部标注「唯一事实源」或「角色包」，并写明「修改须用户明确确认 + 记录变更原因」。

### 章节文件规范（chapters/）

- **路径**：`chapters/第NN章-标题.md`（NN 两位数序号）。
- **不按幕分文件夹**：幕（第一/二/三幕）是故事结构，写在 03-故事线里，不是文件目录。
- **无 frontmatter**：章节是纯 Markdown，直接 `# 第NN章 标题` 开头，不要 YAML frontmatter（title/type/novel/chapter/act/status/created/tags 都不需要）。
- **frontmatter 是发布阶段的事**：只有走 novel-site-publish 发到 Hexo 站点时才加四件套 frontmatter，创作阶段保持纯净。

## 写正文章节 SOP（框架冻结后，每章走一遍）

1. **写前列清单**：扫本章大纲，列出所有现实细节（时间/地点/商品/价格/人物/事件/装备）。
2. **四分法归类 + 查证**：硬事实、地方事实→查证（先查 06 细节库，没有就联网查「最小行政单位」词条）；不可验证→替换/模糊化；纯虚构→自洽即可。
3. **过两道关**：时间性（故事年份有了吗）+ 匹配一致性（组合合理吗：油品/弹容/里程/规格）。
4. **写正文**：只引 05 台账 + 06 细节库里「✓已查证」的数据；没有来源的真实细节一律不写。
5. **写后校验**：扫正文现实细节，对照台账确认「没编造、有来源、前后一致」。
6. **回写台账**：本章新确定的现实细节，当场回写 05（时间线/已定事实）+ 06（带来源）。
7. **年龄/时间推进校验**：角色年龄 vs 故事年份对齐（如主角 X 年生，故事起点 N 岁，故事终点 M 岁），年龄、车龄、时间线不得打架。
8. **发布衔接**：章节完成后如需发布站点，走 novel-site-publish（frontmatter 四件套 + 双副本同步检查）。

### 返稿/拦截（冲突即拦，不硬写）

出现以下任一情况，立即拦截返稿：
- 正文与 00-权威设定冲突 → 以 00 为准
- 正文出现台账/细节库没有的「真实细节」（疑似编造）→ 补查证入库，或模糊化/替换
- 同一事实前后两处说法不一 → 以 05 台账为准
- 时间性错误（写了当时没有的东西，如写某高速当年尚未通车）
- 匹配一致性错误（组合不合理，如涡轮车加低标号油）
- 对白用了方言字 / 出现禁止内容

## 角色管理：核心角色 + 涌现机制

不要一开始就设定所有角色。角色分两层：

### 核心角色（立项时设定，约 6–10 个）
- 主角、女主、核心配角（兄弟团、家人）。
- 动机、弧光、软肋、秘密、关系完整设定。

### 涌现角色（写故事时按需生成）
- 剧情需要「有名字、有对话、有剧情作用、可能再出现」的新人物时，当场涌现。
- 路人甲（门口保安、一次性背景）**不建卡**。
- 涌现流程：
  1. 剧情推进需要新角色（如「主角去某电子市场遇到档口老板」）。
  2. 基于剧情上下文，生成**最小够用**角色卡（身份 / 性格 / 与主角关系 / 语言），写入 `04-角色包/`，frontmatter 标 `type: character` + `tags: [涌现]`。
  3. 后续该角色再出现，查角色卡保持一致。
- **最小够用原则**：只设剧情需要的部分，弧光/秘密可留「待定」，后补。
- **防止泛滥**：一次涌现只建 1–2 个；一次性路人、纯背景不建卡。

## 现实世界细节验证系统

小说里的每个现实细节都要经得起推敲，让懂行的读者无可挑剔。核心不是「每个细节都查」，而是**分层处理 + 替换策略 + 时代细节库**。

### 细节四分法（写前先分类）

| 层 | 内容 | 处理 |
|---|---|---|
| 硬事实 | 历史事件、著名人物、物理/商品参数、全国性价格、法律 | 联网查权威来源，精确引用 |
| 地方事实 | 地方物价、地理、地方小新闻 | 能查则精确；查不到→模糊化 |
| 不可验证 | 具体街名、具体店铺、微观细节 | **替换为可验证等价物 或 模糊化** |
| 纯虚构 | 角色、情节、对话 | 自由创作，但内部自洽 |

### 时间性验证（哪年才有）

现实细节不仅要「存在」，还要「故事发生的年份**已经**有」。重点查：高速路网、产品/车型、App/软件、政策/法规、地名/行政区划。

- 例：某年某省高速路网远不如现在——某条高速（数年之后才通车）当时根本没有，主角只能走更早通车的另一条高速。写「当年走这条高速」就是穿帮。
- 查证方法：搜「XX 通车时间」「XX 哪年上市」「XX 上线时间」「XX 政策哪年实施」，把「哪年有」钉死，写进时代细节库。

### 匹配一致性验证（物理/工程/常识自洽）

现实细节之间要互相匹配，不能「看着像、实则穿帮」。典型穿帮：

- **车辆 vs 油品**：涡轮增压车型加 95/97，写「加 93」会爆震伤机；自然吸气车型加 93 才对
- **枪械 vs 弹容量 vs 伤情**：手枪弹匣 7–17 发，写「几十发不换弹」是穿帮；步枪弹打中肢体是毁伤性创伤，写「只是流血」是穿帮
- **距离 vs 时速 vs 耗时**：高速约 100km/h，350 公里约 4 小时，写「1 小时到」是穿帮
- **设备 vs 当时规格**：某年手机性能、网速、App 版本
- 校验法：把主角「开的/用的/穿的/吃的」串起来问一句「这个组合在现实里成立吗」；拿不准就查该事物的参数（油品标号、弹容量、里程、规格）。

### 细节填充原则（尽力真实，模糊化是最后手段）

1. **优先尽力挖真实**：涉及真实地点/餐馆/街道/物价，尽量联网深挖（地方志、新闻报道、地图、点评、物价记录），把「吃顿饭在哪吃的」都落到真实信息上。

**深挖方法（关键：别泛搜大词）**：
- 泛搜「某地美食」「某地老字号」只会命中全国的百科站、营销号、别的城市的同名店——这就是「在维基百科百度谷歌随便看看」。**查地方事实要搜「最小行政单位」的具体词条**：搜「某镇」命中该镇的百科词条，能带出下辖村全名单、地名沿革典故、河流纵穿镇境、主导产业、省道/铁路/高速——这些才是本地人一眼能验证的细节。
- 优先挖本地化源：地名数据库（如博雅地名网 tcmap.com.cn，按省市县镇村层级列全）、地址/邮编库（小区地址、门牌号暴露真实路名）、地方报纸专版、省情网地方志、地图 POI。
- 搜路名用「某市 XX 路 地址 号」或查小区/酒店/公园的门牌地址，而不是直接搜「某市有什么路」。
- 查完把「最小行政单位」词条本身读透（百科的镇级词条往往已含村名单、地名沿革、地理、经济），比反复泛搜有效得多。

2. 查到了 → 写具体真实（「在某市 XX 路的大排档」），可追溯到来源。
3. 实在查不到 → 三选一降级，**绝不硬编**：
   - **模糊化**：「那几年」「镇上」「大概」「百来块」。
   - **替换同类可验证**：查不到「XX 牌子的烟」→ 换成当时真实存在且可查价的畅销烟。
   - **时代通用意象**：某年 = 当年主流手机、刚兴起的 App、当时的物价水平。

### 时代细节库（预先建立，安全牌）

- 每个时代背景建一套「时代细节库」：常见商品及价格、流行、社会现象、技术状态。
- 写小县城/时代场景时，从库里取「可验证的安全牌」，既真实又可追溯。
- 例（2013 年库）：某畅销烟 XX 元/包（当前价，当年价待查）、BTC 2013 年 4 月破百美元→266→跌破 50、iPhone5、微信上线、余额宝 2013-06 上线。
- **示例中的价格若未标注来源，一律视为「待查」，不得直接写入正文**（查不到就模糊化，绝不硬编一个数）。

### 查证铁律
1. 涉及真实数据/事件，写前查证（宿主提供联网检索能力）。
2. 记录来源：URL + 标题 + 原文引句 + 查询日期。
3. 无来源数据**禁止入文**。
4. 查不到确切值 → 模糊化或替换，**绝不编造**。
5. 动态数据（价格/政策）标注时间点，过期重查。
6. 来源冲突 → 标注冲突、采信权威来源，不静默选边。
7. **查证前先查已有事实库，勿重复考据**：若已加载 `historical-price-research` skill（专为小说年代考据），先查它的 `references/` 目录——同作品同章节可能已有核验过的事实库（物价/油价/油耗/逐日价），直接复用；`maps` skill（OpenStreetMap 地名/坐标/POI）可查地理坐标与边界，但中国本地餐馆/小路覆盖弱，别当主力。

### 数据台账（写入 05-连续性台账 + 时代细节库）
每条已查证事实：
```
- 事实：<具体数据/事件>
- 来源：[标题](URL)
- 原文引句："…"
- 查询日期：YYYY-MM-DD
```

### 写章节查证流程
1. 写前先列本章涉及的「真实细节」清单（含时间、地点、商品、人物、事件）。
2. 逐个分类：硬事实 / 地方事实 / 不可验证 / 纯虚构。
3. 硬事实 + 地方事实 → 查证记录进台账；不可验证 → 替换或模糊化；纯虚构 → 自洽即可。
4. 正文只引用台账已查证数据 + 时代细节库的安全牌。
5. 同一数据前后一致——台账是唯一权威，冲突即拦截返稿。

### 诚实边界
- 能保证：硬事实精确、地方事实尽力、不可验证的替换/模糊化、绝不编造、前后一致、可追溯。
- 不能保证：某年某市某条街的真实店名（客观上可能无资料）——正确做法是替换或模糊化，而不是硬编一个假的。

## 跨宿主说明

本 skill 的**流程、模板、数据文件宿主无关**（纯 Markdown + 对话提问），任何 LLM agent（Hermes/Codex/其他）加载后都能跑同一套流程。

但**查证依赖宿主提供联网检索能力**（Hermes 的 web_search/web_extract、Codex 的 web 工具等），本 skill 不绑定具体工具名，只要求「宿主能联网查证」，任何等价能力皆可。宿主无联网能力时，查证退回「模糊化/替换/标待查」，绝不凭模型记忆硬编。

## 常见坑

- 一次性问太多问题，用户答不动 → 每次 2–4 个。
- 停在"看感觉"就往下走 → 必须追问到可执行。
- 框架没冻结就开始写 → 先冻结权威，再动笔。
- 世界观、风格、故事线混在一堆 → 分文件、分阶段，互不污染。
- 角色弧光只有"变强/成功"没有"代价" → 追问弧光的代价。
